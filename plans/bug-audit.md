# Performance and correctness audit

Reviewed revision `845a6c123`. The audit contains 20 findings and one unresolved DAX durability question. Prioritize the reproduced state loss in findings 1 and 16. Findings 2, 3 and 9 have isolated progress or operation-count evidence. The experiments below identify their controls and limits. Production latency remains unmeasured.

## Persistence and progress

1. **A failed delete can become durable.** In `crates/extent_files/src/file_set.rs:518`, delete removes the file from the live map before reading its extent tree. A read error at line 526 returns to the caller with the file already absent. The next successful commit of another file builds the root from that map at line 575, making the deletion durable and omitting the removed file's extents from reclamation. Keep the file in the live map until the replacement root commits. Verify that an injected tree-read failure leaves the file readable both immediately and after committing a different file and reopening.
2. **A persistent write-back error can stall every store sharing the page cache.** In `crates/local_cell/src/pages.rs:372`, writers wait until the shared dirty count falls below the hard limit. Failed writes retain dirty pages at line 719, and the live flusher logs the error at line 425. If the failing file alone exceeds the bound, a writer targeting a healthy file can wait indefinitely. Give admission a way to return the write-back failure while preserving dirty data and the memory bound. Exercise a healthy writer with a different file failing above the bound.
3. **Cancelling a cold read can strand a bucket request slot.** In `crates/bucket_cell/src/fetch.rs:1034`, the tail cache owns a shared future even when its last reader goes away. If cancellation happens during the GET at line 1046, the slot stays in that suspended future. At a request limit of one, a different cold object can wait indefinitely. The daemon façade at `crates/cladefs/src/bucket.rs:481` spawns its inner read task, so dropping that outer handle alone leaves the GET running. The demonstrated cancellation applies to a directly polled fetch. Tie pending tail lifetime to its readers as part fetches already do at line 899. Verify both last-reader cancellation and one reader cancelling while another still awaits the same tail.
4. **Revoking a tenant can unlink its newly granted socket.** In `crates/cladefs/src/cladefsd/grants.rs:106`, revoke releases the grants lock before unlinking. A grant in between can replace the stale socket and return the same pathname. The earlier revoke then unlinks the new listener. Serialize name removal with creation and check that a fresh connection succeeds after a regrant under this interleaving.
5. **Disk recount can release quota for pending data.** In `crates/cladefs/src/cladefsd/disk.rs:209`, failed write-back only logs. Recount replaces the previous admission estimate using the directory walk, which can miss completed writes still held dirty after failure. Preserve the conservative charge on error. Check admission after injecting a write-back failure between a completed write and recount.
6. **Concurrent cache fills can consume the configured free-space floor.** Two different fills can sample the same free space before either write at `crates/bucket_cell/src/cache.rs:435`. Admission at line 447 reserves capacity, but each free-space check covers only its own pending write. With room above the floor for one part, both can be admitted. Account for outstanding disk allocations when admitting both tails and parts.
7. **A failed worker spawn can leave its caller waiting forever.** In `crates/cladefs/src/cladefsd/pool.rs:60`, the job enters the queue before the worker starts. If there are zero workers and spawn fails, the queue retains the reply sender and the caller at line 87 waits until another submission starts a worker. Exercise a single submission with a failed spawn and require an observable failure.
8. **A failed flag change can affect the live inode.** In `guest/linux/fs/cladefs/super.c:926`, the live flags and ctime change before persistence returns its result. Setting immutable can therefore fail while subsequent writes are refused. Check GETFLAGS and write access after a failed attribute write and after inode eviction.

## Performance

9. **Sparse page write-back does quadratic work under the file lock.** In `crates/local_cell/src/pages.rs:684`, each run restarts its search at the beginning of the requested range. Line 731 scans again for remaining dirty pages. Flushing N isolated dirty pages revisits a growing clean prefix, yielding quadratic page inspections. Index dirty pages or advance through a bounded generation. Verify inspection counts for increasing sparse files and preserve concurrent redirty semantics.
10. **Disk accounting repeats a process-wide cache traversal for every tenant.** Every ten seconds, `crates/cladefs/src/cladefsd/disk.rs:275` loops over live disks. Each recount calls process-wide write-back at line 209, which visits every registered file at `crates/local_cell/src/pages.rs:296`. T disks and F registered files therefore incur at least T × F file visits per pass, even on an idle host. Scope write-back to each disk or share one correctly ordered flush across the pass. Verify counter snapshots still cover writes admitted during recount.
11. **Seeking across a sparse guest file scales with its logical size.** In `guest/linux/fs/cladefs/super.c:949`, the extent walker advances by at most 1 MiB, including on an empty result. SEEK_HOLE at zero in a 1 TiB all-hole file performs 1,048,576 lookups to return zero while holding the shared inode lock. SEEK_DATA traverses the same holes. Return the next extent offset or end-of-file from the extent lookup. Include an operation-count assertion and check FIEMAP, which shares the walker.
12. **DAX write-back scans all resident ranges three times for a single dirty page.** In `guest/linux/fs/cladefs/dax.c:2377`, write-back counts dirty ranges across the entire array, repeats the count under the exclusive semaphore at line 2397, then walks the array again at line 2405. Index dirty ranges and retain the exclusive recheck. Measure one dirty page as clean mapped ranges increase.
13. **Unexpected local cache errors turn into bucket traffic.** In `crates/bucket_cell/src/fetch.rs:998` and line 1060, local part and tail read errors are logged and treated as misses. A persistent I/O failure can incur a GET each time the in-memory copy is absent. Propagate unexpected errors while preserving genuine misses and CRC eviction. Inject local EIO and assert that it reaches the caller without a GET.
14. **Grant lookup resolves the same path once per candidate while holding the global lock.** In `crates/cladefs/src/cladefsd/grants.rs:90` and line 98, each directory comparison invokes `in_dir`, which calls `store_key` at `crates/cladefs/src/cladefsd/server.rs:952`. An unmatched path incurs filesystem lookups for every grant, blocking other grant operations meanwhile. Resolve each input once, then compare it against canonical tenant directories.
15. **Closing an uncommitted file leaks a mapping region.** Mapped open pops a region at `crates/extent_files/src/file_set.rs:292`. Last close of an uncommitted file removes its record at line 423 without returning its region. Repeated create/close without sync exhausts the finite region pool, leaving later files without mapped reads until reopen. Verify a one-region file set can still map a committed file after creating and closing an empty uncommitted file.

## Additional findings

16. **A failed partial-page truncate silently drops earlier writes.** In `crates/extent_files/src/pages.rs:659`, shrinking removes all dirty chunks beyond the new end before the fallible read of the retained partial page. On error, the old file size stays in force, but reads can return old committed bytes in place of previously accepted writes. A later successful sync preserves the wrong contents. Prepare the retained page before discarding any dirty chunks. The existing crash test in `crates/extent_files/tests/crash.rs` checks committed images but does not combine an outstanding overwrite with a read failure during shrink.
17. **Committing a sparse shrink allocates memory for every removed logical block.** At `crates/extent_files/src/pages.rs:761`, the commit plan inserts even absent blocks into a tree set, then collects parents and loads nodes to identify extents to release. Shrinking an all-hole file to zero does this with zero data extents to free. Walk allocated subtrees and skip absent children. The allocation probe below measures this separately from file creation.
18. **A contiguous memory-cell read issues a device read for each 4 KiB block.** The first-touch mapper calls `FileSet::read` to warm a node before mapping its runs at `crates/cladefs/src/memory_cell.rs:382`. The read loop at `crates/extent_files/src/pages.rs:578` awaits each unmapped block separately. With metadata already available, the probe counted 170 serial device reads to fetch one contiguous 680 KiB run. TASK-456.3 deliberately installs a node ahead of subsequent faults. The avoidable work is the per-block request inside that operation. Coalesce adjacent clean blocks in the same extent while respecting device limits and dirty overrides. The count is at the Device boundary and does not imply 170 bucket GETs.
19. **The follower history checker accepts held-file reads going backward.** At `crates/follower_history/src/lib.rs:262`, held reads are checked independently after named reads have been checked in sequence. A held object can return the new value then the old value to one reader, and the history passes if each result is individually plausible. This weakens the simulator and guest test oracle. It provides no evidence that a live follower returned stale data. Preserve operation order across both read kinds.
20. **A virtio queue can report successful startup after its event loop fails to initialize.** At `crates/virtio_extent/src/workers.rs:171`, worker creation reports success once the thread is spawned. Creation of its epoll descriptor and registration of its queue and stop descriptors happen inside the thread at lines 206–221. Failure there logs and returns without servicing the queue or propagating startup failure. Verify startup fails on a refused epoll registration and rolls back other workers. Source-traced only.

## Validation results

All probes ran on arm64 macOS in a temporary directory. File-set, SQLite and history probes linked the worktree's implementation. The page-cache and tail probes isolated the relevant implementation from the daemon. No regression tests were installed in the project.

The page-cache probe used the production page and frame code with counters, standard synchronization, a memory sink, a temporary byte buffer, and a stub for the flusher's process panic annotation. The sparse-shrink probe measured heap allocation with a fake extent device. Neither measures disk throughput.

**Considered and excluded.** A two-database SQLite transaction recovered with one update present and one absent in two simulated crash images under DELETE journaling and FULL synchronous mode. TASK-296 explicitly records separate commits for attached databases as a design limit, so this is excluded from the finding count.

## Durability race requiring a scheduled test

The two passes in `guest/linux/fs/cladefs/dax.c:2550` count and collect busy files under the membership lock. Dirty and private counters can change between passes. A lower-numbered inode becoming busy can take the last array slot, displacing an inode that was busy throughout. The sync path at line 3980 waits for write-back only on the collected files. Check whether this lets syncfs return before an older write-back commits by pausing that write-back, introducing the lower-numbered inode between passes, and checking the durability boundary. The collection omission follows from the code. Linux sync also runs inode write-back before its final filesystem sync. That can already wait for a VFS-dirty inode, and the simulator calling settle directly does not exercise that protection. Whether an omitted inode can still have outstanding writes at the final seal remains unverified.

Coverage was weighted toward first-party storage, daemon and guest paths. Vendored dependencies, generated bindings and every upstream Fxfs module did not receive a line-by-line review. Guest-kernel findings in this report remain source-traced. No Linux or end-to-end performance run was made.

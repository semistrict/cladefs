# libmachine's architecture

libmachine (`crates/libmachine`) is a Rust **library VMM** on Hypervisor.framework: it runs cladefs's Linux guests on an Apple Silicon Mac. It came from semistrict/libmachine at cbff5b1, copied into this repo on 2026-11-26 (board 13054) and relicensed BSD-3-Clause; its Backlog tasks are on the board (`tag.libmachine=yes`, label `libmachine=TASK-N`), and this document was its doc-1. cladefs's Firecracker (`vendor/firecracker`) is the production VMM on Linux: the two VMMs share the extent device (`crates/virtio_extent`) and the guest kernel.

**What is here, and what is not (the user, 2026-11-27, board 14519).** libmachine is in this repo so that cladefs's guests run on a Mac (`crates/libmachine-firecracker`, a Firecracker-compatible VMM on libmachine, which cladefs's guest tests run as `CLADEFS_FIRECRACKER`), and so that hotbed's Mac worker has a VMM (`crates/machined`). Everything else libmachine carried in from its former life was removed in one change: the KVM and x86-64 backend, suspension, the `Sandbox` layer, the Python bindings, the network stack's own save and restore with the patched smoltcp, machined's calls for stops, watches, execs, files, snapshots, suspensions and balloon targets, and the doc-1 sections that described them. What the deleted code did and why is in git history (the commit before board 14519's) and doc-31's records, whose entries about removed parts stay as the history of why they were made.

**End goal:** a macOS machine on Apple Silicon running cladefs guests in full (the user, 2026-11-26): the guest runs Fxfs in its Linux kernel on the virtio extent-store device, its file data mapped by DAX from the host's `cladefsd`, so every VM on a host shares one copy. Much of the design below follows from that device.

## Platforms
- **macOS on Apple Silicon** (raw Hypervisor.framework, arm64; board 13063; macOS 15 and later) is the only platform, and runs cladefs's guests in full, DAX included. The VMM is its window's second stage itself: Hypervisor.framework maps guest memory page by page (`hv_vm_map`), and a guest's access to a window page it has not mapped exits to the VMM (board 13069).
- The guest is aarch64. A snapshot only restores on the same host CPU (its fingerprint is checked).

## Guest
- A real Linux kernel: **cladefs's guest kernel** (Linux with Fxfs, from `guest/linux`, built by `scripts/build-guest-kernel.sh` for both architectures), the one Firecracker boots (board 13061), plus libmachine's agent in the guest. Root filesystems are Fxfs stores (below).


## The arm64 board on Hypervisor.framework (board 13063)
- **Backend** (`backend/hvf`): the framework's C API declared by hand (`ffi.rs`, from the SDK's headers; no bindgen). The framework gives a process **one VM**: one machine at a time per process, a second refused. A vCPU belongs to the thread that creates it: each is created on its vCPU thread at its first run and destroyed as that thread exits. Kicks are `hv_vcpus_exit`, which latches for a vCPU not running.
- **What a kernel hypervisor does in the kernel, the VMM does here:** ioeventfds (a guest write to a queue's notify address exits, and the vCPU signals the queue's event), irqfds (a thread per VM waits on every MSI-X vector's event and sends the route's MSI with `hv_gic_send_msi`), PSCI 1.0 over HVC (CPU_ON, CPU_OFF, AFFINITY_INFO, SYSTEM_OFF, SYSTEM_RESET), WFI if it exits (the vCPU thread sleeps until an interrupt is sent or its virtual timer would fire; with the framework's GIC it does not: the framework waits in `hv_vcpu_run`), and system registers the framework leaves to the VMM (read as zero, writes ignored). The devices signal events (`sys::EventFd`, a pipe: macOS has no eventfd) and wait on them with poll(2) (`sys::wait_readable`).
- **Platform:** the framework's GICv3 (macOS 15+) with its GICv2m MSI frame, the architected timers (the virtual timer's PPI 27 the GIC's own), a 16550 at MMIO, PCI ECAM (bus 0) with MSI-X only, described by a device tree (`arch/aarch64/fdt.rs`: `/chosen` with `rng-seed`, `/psci` method hvc, `pci-host-ecam-generic` with `msi-parent` the v2m frame). The kernel is cladefs's arm64 `Image` (4 KiB pages), entered at EL1h with x0 the device tree's address.
- **Address map** (`arch/aarch64/layout.rs`, fixed, 40-bit IPA so 4 KiB stage 2 pages work): GIC distributor 0x0800_0000, MSI frame 0x0801_0000, UART 0x0802_0000, redistributors 0x0900_0000 (32 MiB: the framework places them for the 256 vCPUs it supports), ECAM 0x1000_0000, 32-bit BARs 0x4000_0000, RAM from 0x8000_0000, 64-bit BARs (the DAX window) from 0x80_0000_0000.
- **Signing:** a process makes VMs only if signed with `com.apple.security.hypervisor`; `scripts/macos-link.sh` (cargo's linker on macOS) signs every executable as it links it, ad hoc.
- **Guests for the tests:** `crates/libmachine/scripts/arm64-guest.sh` builds cladefs's arm64 kernel and the test initramfs on an arm64 Linux node of hotbed's and fetches them into `target/arm64-guest`.
- Base kernel command line: `console=ttyS0 panic=-1` (a panic resets the machine).
- The test guest is libmachine's own initramfs (`guest/init.c`, the agent, busybox; `scripts/build-test-guest.sh`) on cladefs's kernel.

## API
- Rust core built on the rust-vmm crates, over one backend (`backend/hvf`). Many VMs per process are not possible: the framework gives a process one VM (below, machined's helper processes).
- A `Machine` (memory, vCPUs, devices, vsock, snapshots, a bare variant for instruction-level tests), and `agent`, the host's client of the guest agent over the machine's vsock.
- **machined** (`crates/machined`, board 13467) is the multi-VM server this library is for: one process, many machines, managed over its own gRPC API (`machined.v1.Machined`: create, start, delete, get, list and console, the calls hotbed's Mac worker makes), on a Unix socket (mode 0600, peer credentials checked) or TCP with mutual TLS; each machine's vsock is reached through a Unix socket speaking Firecracker's protocol (`vsock`), and each machine's VM runs in a helper process of its own (board 13460).

## Virtio transport: PCI only (decision)
- Every virtio device attaches over **virtio-PCI** (modern, virtio 1.x) with MSI-X; there is no virtio-mmio transport.
- Why: cladefs's extent device is PCI-only for performance (TASK-273). cladefs measured writes and commits about 40% faster than over MMIO (121 µs -> 73 µs a write) and about 1.3 instead of 4.6 VM exits per request, because MSI-X interrupts are injected by the hypervisor instead of the guest reading and acking an MMIO interrupt status (`docs/measurements/virtio-pci-vs-mmio-2026-11-09.md`). One transport for all devices keeps the device code single-path.
- Requirements this brings: a PCI host bridge, MSI-X routed through the backend's irqfd thread, ioeventfd queue notifications, 64-bit BARs, shared memory regions as a BAR with `VIRTIO_PCI_CAP_SHARED_MEMORY_CFG` capabilities, and device types past 63 (the extent device is 0x4658), which take PCI device ID 0x103f, the last transitional ID, with the type as subsystem ID: upstream Linux reads 0x107f as type 63 and binds no ID past it (decided in board 13111).
- **The PCI platform (board 13111):** one conventional PCI host bridge in the device tree (`pci-host-ecam-generic`, segment 0, bus 0 only) with the address map's 32-bit and 64-bit BAR windows; configuration space through ECAM only; BARs assigned before boot with memory decode on, as firmware does; interrupts MSI-X only (no INTx, no `_PRT`). Each virtio device's queues run on one device thread per machine, woken by ioeventfds; every board machine has a virtio-rng.

## Storage
- **The daemon runs in libmachine's process** (the user, 2026-11-26): libmachine is a library for one large multi-VM server process, and requires no external `cladefsd`. It embeds cladefs's daemon (libcladefs), one per process, shared by every machine in it (`ExtentDaemon::start`, or `ExtentDaemon::embedded` for a daemon its embedder booted), and connects their extent devices to it in memory (`libcladefs::Daemon::connect`, board 13553); an extent store names a new cell of a tenant's, an existing cell, or a cell directory (`ExtentCell`). `ExtentDaemon::at_socket` reaches a daemon outside the process. Firecracker keeps its external daemon.
- **macOS: a helper process per VM** (the user, 2026-11-26): Hypervisor.framework allows one VM per process (a second `hv_vm_create` returns HV_BUSY), so on macOS each VM's vCPUs and devices run in a helper process libmachine spawns, reaching the server's daemon over cladefs's VM-process wire, its DAX pages through shared memory (board 13460). The API is the same on both.
- Root and data filesystems are **Fxfs on the cladefs extent device** (spec: doc-4, copy-on-write DAX: doc-13). Bases are imported from OCI images (`cladefsctl import`) and each VM gets a fork.
- The device's DAX window is guest-physical address space (up to 64 GiB). libmachine is the window's second stage (board 13069; `crates/virtio_extent/README.md` lists an adapter's obligations).
- The guest writes at most `private_max` private pages through the window; past that the VM stops.
- virtio-blk overlays are dropped from the plan. virtio-fs stays deferred.

## Host I/O (v1)
- virtio-vsock RPC to the guest agent. The agent follows cladefs's reconnect rules: a new connection per exchange, a reset means "connect again", only idempotent asks are resent (cladefs `docs/integrator-guide.md`).
- **virtio-vsock (board 13089):** every board machine has one (guest CID 3, stream sockets only), its host end in-process (`Vsock`: connect, listen, reset all connections), not Unix sockets or vhost-vsock: CIDs are per machine and there are no socket files. Credit flow control both ways; after a transport reset (a restore) no connection is made until the guest has taken it (reposted its event buffer): the guest's own connects are refused, a host connect waits for it within its timeout (board 13177). While a reset is under way the device sets the event queue's avail event index to the index it saw, so that the guest's repost (Linux keeps 8 event buffers posted) notifies it at once. The next host port is part of a snapshot, so that a clone never connects from a port of a connection its guest may still hold from before. When a run ends with the guest powering off, resetting or triple-faulting, every host-side stream, connect and accept fails at once with a reset (`is_guest_stopped`) until the guest's driver starts the device again (board 13133); the signal is the run's outcome, in `Machine::run`.
- **Guest agent (board 13089, board 13131):** `libmachine-agent`, Rust, static musl (crate `crates/libmachine-agent`, whose library is the wire protocol both sides build), listening on vsock port 100. Protocol v3 (v1 and v2 refused, never converted): an `lmag`+version preamble each way, the agent's `Hello` with its random instance number and the restore generation it last reseeded for, then framed messages, one exchange per connection: reseed (after a restore, before anything else), ping, exec (with a host-chosen request ID; streamed stdin, signals, stdout/stderr, exit, `Release`), attach (take a command up again from output offsets), read a file, write a file (temp + rename). Commands live apart from connections in the agent: an exec whose ID it knows attaches instead of running again, so the host resends execs after any reset; a process whose connection is reset is taken up again from its output offsets, the client resending the stdin and signals the agent had not taken (each arrives once). Output is kept 512 KiB behind what was sent (more than the vsock has in flight) and read at most 256 KiB ahead (the command waits rather than output being lost); an orphaned command runs 60 s for its host to come back, a finished one's result is kept 60 s, forgotten IDs are never run again. A changed instance (the agent restarted) or a forgotten command fails with `Error::ConnectionReset`; a stopped guest with `Error::GuestGone`.
- **virtio-net and the egress policy (board 13097):** optional (`MachineConfig::network`, off by default: a machine has no network unless asked), features MAC, MTU (65520: large frames instead of checksum/TSO offloads) and MRG_RXBUF. The other end is a smoltcp 0.12 stack in AnyIP mode on a network thread of its own (the device thread only moves frames): the guest is `10.0.2.2/30` with hostname `guest`, configured by `ip=` on the kernel command line (needs `CONFIG_IP_PNP`; ~15 ms of boot), and the VMM is its gateway and DNS server at `10.0.2.1`, which also stands for the host's loopback. A guest SYN is held while the VMM connects from the host with an ordinary non-blocking socket; then a smoltcp socket listening on exactly that destination takes the replayed SYN, or, if the policy denied it or the host connect failed, smoltcp answers the replayed SYN with RST (connection refused, at once). TCP only, IPv4 only; UDP reaches only the DNS server (A records from the host's resolver for names the policy could allow, AAAA empty, NXDOMAIN otherwise); ICMP echo only to the gateway. The policy (`net::EgressPolicy`): ordered rules (allow/deny, host pattern, port range), first match wins, default deny; host patterns `*`, IP, CIDR, DNS names (exact or `*.domain`, matched against the names the guest resolved through the VMM); `*` and names match only globally routable addresses (no loopback, private, link-local or metadata addresses: those need an explicit IP/CIDR rule), against SSRF and DNS rebinding. Changeable at runtime (`Machine::network()`). Limits: 128 connections, 256 KiB buffers each way. A machine with a network is not snapshotted: its connections are host sockets no restored machine could share. **Around the policy (board 13151, board 13157):** an `ask` rule hands a connection to the caller's `Decider` (a callback with a timeout, default 10 s, and a default verdict, default deny), called on a decider thread of its own per machine, one question at a time, never on the network thread; the guest's SYN waits for the answer or the deadline (then the default; a late answer is ignored; a panic or no answer is the default too; questions whose time ran out are not asked); no decider means deny. Every connection is logged when it ends (denied ones at once): guest port, host address and port, the names it went by, verdict, what decided it (rule, no rule, callback, callback timeout/failed, no callback, connection limit), whether the host connection was made, bytes each way, start time and duration, in a ring per machine (`NetworkConfig::log_capacity`, default 1024) the caller drains (`Network::take_log`), the oldest dropped and counted when full; `Network::stats` gives counters (connections allowed/denied/failed/open, bytes each way live, DNS queries and refusals, decisions asked/timed out/failed, log records dropped). DNS answers carry `NetworkConfig::dns_ttl` (default 60 s; the host's getaddrinfo gives no TTL, so the VMM is the authority), and a name learnt from one matches name rules for its addresses for exactly that long, open connections staying. Caller-set host entries (`net::Hosts`, runtime `Network::set_hosts`) are answered by the VMM's DNS before the host's resolver, only for names the policy could allow, 127.0.0.1 answered as the gateway; a name rule matches an entry's addresses whatever they are (the caller set the mapping), while learnt names still match only global addresses. Fuzzed: `crates/libmachine/fuzz` (`net_frames`: the whole guest ingress with a fake host; `dns_query`).

## Snapshots
- **Taking one:** `Machine::snapshot(path)` (or `snapshot_with`, which puts the RAM in a file of its own as Firecracker's memory file, or has its caller keep it, as a memory cell's version) between runs: every vCPU is parked (`&mut` means no `Run` exists; each vCPU finishes the access of its last exit when a run ends, so the state read is what the guest resumes from) and the device thread is held off by holding every virtio transport's lock for the whole snapshot, so nothing writes guest RAM meanwhile. Refused for a machine with a network, nested virtualization or pmem devices.
- **The file:** a 64-byte header (magic, format version 4, state length, RAM offset, the state's SHA-256), the state (own little-endian codec), then each RAM region at a 2 MiB multiple, zero pages left as holes where the filesystem keeps them. Written beside its path, synced and renamed over it, read-only for its owner (clones map it: it must not change under them). The state: the CPU's fingerprint, vCPU count, RAM size, the memory layout, the balloon, disks and extent store devices, the caller's data, then the GIC's and the host's clock, every vCPU's registers, the UART's, the RTC's and every PCI function's with its device's. libmachine's snapshot files are outside `formats/`: a change bumps the version, and the new code refuses every other by name.
- **Restoring:** `Snapshot::open(path)` checks a file once; `Machine::restore(&snapshot, config)` makes a machine from it, any number of times, one at a time in a process. Refused, never converted: another format version, a damaged file, a config of another vCPU count, RAM size (whole memory layout compared), a CPU fingerprint this host differs in, a network. `Machine::restore_onto` restores onto RAM its caller keeps. Guest RAM is a MAP_PRIVATE copy-on-write mapping of the snapshot file: a clone's writes never reach the file or other clones.
- **Clock and RNG:** the guest's virtual counter goes on from the snapshot's count, so no time passes for it while it was in the file; a restored device sends the guest a transport reset event (below), and the guest agent reseeds the guest's RNG with host entropy before running anything (the restore generation in its `Hello`).
- **vsock:** a restored device sends the guest a transport reset event, so it drops connections from before the snapshot; new connections wait until it has taken it (the guest's repost of its event buffer notifies the device), and its host ports carry on from the snapshot's.
- The extent device follows doc-4's snapshot protocol (board 13139): the guest's Fxfs is frozen (`FREEZE`) before the snapshot, which is refused otherwise; the snapshot records what the window maps, not its memory; a restore forks the store from the snapshot's point and maps the window again at the same guest physical address.

## Security and tenancy (decision)
- The VMM runs inside the caller's process and restricts its own threads: seccomp filters on vCPU and device threads on Linux. On macOS and Windows we rely on Rust's memory safety and a small device set (acceptable while they are developer platforms).
- **One libmachine process may run VMs for many tenants.** This is a deliberate departure from cladefs's integrator model, which treats each VM process as compromised and jails one VM per process with a per-tenant daemon socket. Accepted risk: a guest escaping into the VMM reaches every tenant's daemon socket and stores held by that process. Callers that need cladefs's isolation can still run one process per tenant.
- Guest-facing parsers (virtio queues, the extent device's requests, smoltcp) must be fuzzed. The network's are (board 13097, `crates/libmachine/fuzz`).

## macOS (decision, 2026-11-26)
- macOS runs the same extent device as Linux, **with DAX** (the user's goal; it overturns libmachine's decision-4, which had dev platforms run it without DAX). cladefs's daemon runs on the Mac (board 13065), embedded in libmachine's process (`libcladefs`, board 13471): its in-process devices reach it through a socket pair, and the helper processes a VM per process needs (board 13460) through the VM-process wire; libmachine there maps the window's pages into the guest itself (board 13069). On macOS the daemon has no FUSE mount, no cgroups or pressure for its governor (its budget from `hw.memsize` and the VM statistics), and no userfaultfd stage; a transfer area is a POSIX shared memory object, which macOS never resizes once sized (hotbed question 566); a VM process's exit is watched by kqueue (hotbed question 567). It runs, DAX included (`crates/libmachine/tests/hvf_extent.rs`): the guest mounts Fxfs from a cell of the daemon embedded in the test's process, connected in memory (board 13553), and maps its files' pages through the window, whose second stage there is `cladefs_core::dax::hvf` (board 13069): the daemon's pages are mapped into the guest as the window maps them (eagerly: no installs left to first touches, as Hypervisor.framework has no mapping budget like Linux's `vm.max_map_count`), from the arenas' memory objects mapped run by run, 4 KiB stage 2 pages (`HV_IPA_GRANULE_4KB`) letting each 4 KiB unit map from anywhere in its arena; a guest's abort on an unmapped window page goes to the daemon (`virtio_extent::window_fault`, counted as `access_retried`), and a write to a mapped page makes it private, a copy in the window's private memory, mapped writable, of `private_max` pages at most.
- HVF builds and VM tests run on the user's Mac: hotbed has no macOS node and GitHub's M1 runners cannot nest Hypervisor.framework.

# libmachine's architecture

libmachine (`crates/libmachine`) is a Rust **library VMM**: callers link it into their own process and create many short-lived Linux micro-VMs, mainly to sandbox code written by AI agents. It came from semistrict/libmachine at cbff5b1, copied into this repo on 2026-11-26 (board 13054) and relicensed BSD-3-Clause; its Backlog tasks are on the board (`tag.libmachine=yes`, label `libmachine=TASK-N`), and this document was its doc-1. cladefs's Firecracker (`vendor/firecracker`) stays: the two VMMs share the extent device (`crates/virtio_extent`) and the guest kernel.

**End goal:** a macOS machine on Apple Silicon running cladefs guests in full (the user, 2026-11-26): the guest runs Fxfs in its Linux kernel on the virtio extent-store device, its file data mapped by DAX from the host's `cladefsd`, so every VM on a host shares one copy. Much of the design below follows from that device.

## Platforms
- **Linux/KVM** (x86_64) is where libmachine began, and the production platform: secure and fast. cladefs's DAX window there is the VMM process's memory, which `cladefs::dax::uffd` maps with userfaultfd (Linux >= 6.1).
- **macOS on Apple Silicon** (raw Hypervisor.framework, arm64; board 13063) runs cladefs's guests in full, DAX included. There the VMM is its window's second stage itself: Hypervisor.framework maps guest memory page by page (`hv_vm_map`), and a guest's access to a window page it has not mapped exits to the VMM (board 13069). Windows (WHP) stays a developer platform, unplanned.
- The guest uses the host's architecture (x86_64 on KVM/WHP, aarch64 on HVF). A snapshot only restores on the backend that made it.

## Guest
- A real Linux kernel: **cladefs's guest kernel** (Linux with Fxfs, from `guest/linux`, built by `scripts/build-guest-kernel.sh` for both architectures), the one Firecracker boots (board 13061), plus libmachine's agent in the guest. Root filesystems are Fxfs stores (below).

## Boot and platform (x86_64, decided in board 13085)
- **Two kernel formats, each through its documented entry point:** an ELF `vmlinux` through **PVH** (uncompressed, so no decompression; entered in 32-bit protected mode with a `hvm_start_info`), and a `bzImage` through the **64-bit Linux boot protocol** (long mode, identity-mapped page tables, `boot_params`). An ELF without a PVH note is refused rather than entered through a third, legacy path. libmachine follows these ABIs itself rather than copying another VMM's choices.
- **Hardware-reduced ACPI:** a FADT whose sleep control/status and reset registers are I/O ports the VMM traps (soft-off -> `ExitReason::Poweroff`, reset -> `ExitReason::Reset`), a DSDT with `_S5_` and the devices (COM1, the PCI host bridge, the VM generation ID and its Generic Event Device), and a MADT (local APICs, I/O APIC, IRQ0->GSI2 override, LINT1 NMI). No legacy PM blocks, no SCI, no RTC, no i8042.
- Consequence: a hardware-reduced platform has **no legacy PIC on Linux**, so every device's interrupt must be described in the DSDT (COM1 is `PNP0501` there). Guest kernels need `CONFIG_ACPI`, `CONFIG_PCI` (ACPICA refuses to load the DSDT without a PCI config space handler) and `CONFIG_PNP` + `CONFIG_SERIAL_8250_PNP`.
- KVM's in-kernel irqchip (PIC, I/O APIC, LAPICs) and PIT; COM1 is rust-vmm's `vm-superio` 16550 with its interrupt delivered by irqfd. On the PC platform unclaimed ports and MMIO read as all ones and writes are dropped, as on hardware.
- Base kernel command line: `console=ttyS0 panic=-1` (a panic resets, so a sandbox never hangs on one).
- The test guest is libmachine's own: upstream longterm kernel (6.18, checksum-pinned) with `guest/test-kernel.config`, built by `scripts/build-test-guest.sh`. Measured: a quiet boot to init and power-off takes ~30 ms (PVH) / ~45 ms (bzImage) from machine creation.
- The guest kernel libmachine ships is **cladefs's** (Linux 6.18 from Amazon Linux with Fxfs and the virtio extent driver), built by `scripts/build-cladefs-guest.sh` from a pinned cladefs commit with cladefs's own build script, then `guest/cladefs-kernel.config` (libmachine's requirements, checked after the merge; it turns off `CPU_FREQ`, since a vCPU's frequency is the host's). It ships as a PVH `vmlinux`, the image cladefs builds for x86_64, booted without decompression. What the configuration enables and why: `guest/cladefs-kernel.md` (board 13087).

## Guest physical address map (x86_64, fixed; board 13113)
| Range | What |
|---|---|
| `0` - 3 GiB | RAM (first part) |
| `0xC000_0000` - `0xE000_0000` | 32-bit BAR window (PCI MMIO for 32-bit BARs) |
| `0xE000_0000` - 4 GiB | platform area: PCI ECAM, I/O APIC `0xFEC0_0000`, local APIC `0xFEE0_0000`, KVM's TSS and identity-map pages |
| 4 GiB - | RAM beyond the first 3 GiB |
| `0x100_0000_0000` (1 TiB) - 2 TiB | 64-bit BAR window (the cladefs DAX window, up to 64 GiB) |

Fixed for every machine, so snapshots keep device addresses whatever the RAM size; RAM is limited to under 1 TiB - 1 GiB, and hosts need at least 41 physical address bits. `MemoryLayout` (public) records the regions and mapped device memory for snapshots. Devices map host memory at runtime through `Machine::memory_slots()`: RAII `MemorySlot`s over lazily backed `MAP_NORESERVE` memory, only inside the BAR windows.

## The arm64 board on Hypervisor.framework (board 13063)
- **Backend** (`backend/hvf`): the framework's C API declared by hand (`ffi.rs`, from the SDK's headers; no bindgen). The framework gives a process **one VM**: one machine at a time per process, a second refused. A vCPU belongs to the thread that creates it: each is created on its vCPU thread at its first run and destroyed as that thread exits. Kicks are `hv_vcpus_exit`, which latches for a vCPU not running.
- **What KVM does in the kernel, the VMM does here:** ioeventfds (a guest write to a queue's notify address exits, and the vCPU signals the queue's event), irqfds (a thread per VM waits on every MSI-X vector's event and sends the route's MSI with `hv_gic_send_msi`), PSCI 1.0 over HVC (CPU_ON, CPU_OFF, AFFINITY_INFO, SYSTEM_OFF, SYSTEM_RESET), WFI if it exits (the vCPU thread sleeps until an interrupt is sent or its virtual timer would fire; with the framework's GIC it does not: the framework waits in `hv_vcpu_run`), and system registers the framework leaves to the VMM (read as zero, writes ignored). The devices are KVM's, unchanged: they signal events (`sys::EventFd`, an eventfd on Linux and a pipe on macOS) and wait on them with poll(2) (`sys::wait_readable`).
- **Platform:** the framework's GICv3 (macOS 15+) with its GICv2m MSI frame, the architected timers (the virtual timer's PPI 27 the GIC's own), a 16550 at MMIO, PCI ECAM (bus 0) with MSI-X only, described by a device tree (`arch/aarch64/fdt.rs`: `/chosen` with `rng-seed`, `/psci` method hvc, `pci-host-ecam-generic` with `msi-parent` the v2m frame). The kernel is cladefs's arm64 `Image` (4 KiB pages), entered at EL1h with x0 the device tree's address.
- **Address map** (`arch/aarch64/layout.rs`, fixed, 40-bit IPA so 4 KiB stage 2 pages work): GIC distributor 0x0800_0000, MSI frame 0x0801_0000, UART 0x0802_0000, redistributors 0x0900_0000 (32 MiB: the framework places them for the 256 vCPUs it supports), ECAM 0x1000_0000, 32-bit BARs 0x4000_0000, RAM from 0x8000_0000, 64-bit BARs (the DAX window) from 0x80_0000_0000.
- **Signing:** a process makes VMs only if signed with `com.apple.security.hypervisor`; `scripts/macos-link.sh` (cargo's linker on macOS) signs every executable as it links it, ad hoc.
- **Guests for the tests:** `crates/libmachine/scripts/arm64-guest.sh` builds cladefs's arm64 kernel and the test initramfs on an arm64 Linux node of hotbed's and fetches them into `target/arm64-guest`.
- Not yet on HVF (board 13399): snapshots, suspensions, the network, Sandbox, the Python bindings.

## API
- Rust core built on the rust-vmm crates, with our own backend trait over KVM, HVF and WHP.
- Async on tokio. Many VMs per process.
- Two layers: a low-level `Machine` (memory, vCPUs, devices, vsock, snapshots) and a high-level `Sandbox` (exec, stdio, file put/get) built on it.
- **Python bindings via PyO3 are a first-class deliverable** and prove the library works from a real consumer.
- **machined** (`crates/machined`, board 13467) is the multi-VM server this library is for: one process, many machines, managed over its own gRPC API (`machined.v1.Machined`: create, start, stop, delete, watch, console, exec, files, snapshots, suspensions), on a Unix socket (mode 0600, peer credentials checked) or TCP with mutual TLS; each machine's vsock reached through a Unix socket speaking Firecracker's protocol. Its one seam over libmachine (`vmm.rs`) is where macOS's helper processes (board 13460) slot in; its README says how to run it.

## Virtio transport: PCI only (decision)
- Every virtio device attaches over **virtio-PCI** (modern, virtio 1.x) with MSI-X; there is no virtio-mmio transport.
- Why: cladefs's extent device is PCI-only for performance (TASK-273). cladefs measured writes and commits about 40% faster than over MMIO (121 µs -> 73 µs a write) and about 1.3 instead of 4.6 VM exits per request, because MSI-X interrupts are injected by KVM instead of the guest reading and acking an MMIO interrupt status (`docs/measurements/virtio-pci-vs-mmio-2026-11-09.md`). One transport for all devices keeps the device code single-path.
- Requirements this brings: a PCI host bridge, MSI-X routed through KVM irqfd, ioeventfd queue notifications, 64-bit BARs, shared memory regions as a BAR with `VIRTIO_PCI_CAP_SHARED_MEMORY_CFG` capabilities, and device types past 63 (the extent device is 0x4658), which take PCI device ID 0x103f, the last transitional ID, with the type as subsystem ID: upstream Linux reads 0x107f as type 63 and binds no ID past it (decided in board 13111).
- **The PCI platform (board 13111):** one conventional PCI host bridge in the DSDT (`\_SB.PCI0`, PNP0A03, segment 0, bus 0 only) with the address map's 32-bit and 64-bit BAR windows; configuration space through ECAM only (MCFG, the 256 MiB window reserved by a PNP0C02 device), no 0xCF8 ports; BARs assigned before boot with memory decode on, as firmware does; interrupts MSI-X only (no INTx, no `_PRT`). Each virtio device's queues run on one device thread per machine, woken by ioeventfds; every PC machine has a virtio-rng.

## Storage
- **The daemon runs in libmachine's process** (the user, 2026-11-26): libmachine is a library for one large multi-VM server process, and requires no external `cladefsd`. It embeds cladefs's daemon, one per process, shared by every machine in it, and connects their extent devices to it in memory (as the simulation's guests are: `cladefsd::guest`, board 13067). Firecracker keeps its external daemon.
- **macOS: a helper process per VM** (the user, 2026-11-26): Hypervisor.framework allows one VM per process (a second `hv_vm_create` returns HV_BUSY), so on macOS each VM's vCPUs and devices run in a helper process libmachine spawns, reaching the server's daemon over cladefs's VM-process wire, its DAX pages through shared memory (board 13460). The API is the same on both.
- Root and data filesystems are **Fxfs on the cladefs extent device** (spec: doc-4, copy-on-write DAX: doc-13). Bases are imported from OCI images (`cladefsctl import`) and each VM gets a fork.
- The device's DAX window is guest-physical address space (up to 64 GiB). On KVM it is backed by host memory that cladefs's window (`cladefs::dax`) maps with userfaultfd; libmachine provides the memslot, a `Prefault` via `KVM_PRE_FAULT_MEMORY`, `cladefs::guest_thread_started` on vCPU threads, and retries `KVM_RUN` when it fails with `EFAULT` while the window is remapped (`crates/virtio_extent/README.md` lists an adapter's obligations). On Hypervisor.framework libmachine is the window's second stage (board 13069).
- The guest writes at most `private_max` private pages through the window; past that the VM stops.
- virtio-blk overlays are dropped from the plan. virtio-fs stays deferred.

## Host I/O (v1)
- virtio-vsock RPC to the guest agent. The agent follows cladefs's reconnect rules: a new connection per exchange, a reset means "connect again", only idempotent asks are resent (cladefs `docs/integrator-guide.md`).
- **virtio-vsock (board 13089):** every PC machine has one (PCI 00:02.0, guest CID 3, stream sockets only), its host end in-process (`Vsock`: connect, listen, reset all connections), not Unix sockets or vhost-vsock: CIDs are per machine and there are no socket files. Credit flow control both ways; after a transport reset (a restore) no connection is made until the guest has taken it (reposted its event buffer): the guest's own connects are refused, a host connect waits for it within its timeout (board 13177). While a reset is under way the device sets the event queue's avail event index to the index it saw, so that the guest's repost (Linux keeps 8 event buffers posted) notifies it at once. The next host port is part of a snapshot, so that a clone never connects from a port of a connection its guest may still hold from before. When a run ends with the guest powering off, resetting or triple-faulting, every host-side stream, connect and accept fails at once with a reset (`is_guest_stopped`) until the guest's driver starts the device again (board 13133); the signal is the run's outcome, in `Machine::run`.
- **Guest agent (board 13089, board 13131):** `libmachine-agent`, Rust, static musl (crate `crates/libmachine-agent`, whose library is the wire protocol both sides build), listening on vsock port 100. Protocol v3 (v1 and v2 refused, never converted): an `lmag`+version preamble each way, the agent's `Hello` with its random instance number and the restore generation it last reseeded for, then framed messages, one exchange per connection: reseed (after a restore, before anything else), ping, exec (with a host-chosen request ID; streamed stdin, signals, stdout/stderr, exit, `Release`), attach (take a command up again from output offsets), read a file, write a file (temp + rename). Commands live apart from connections in the agent: an exec whose ID it knows attaches instead of running again, so the host resends execs after any reset; a process whose connection is reset is taken up again from its output offsets, the client resending the stdin and signals the agent had not taken (each arrives once). Output is kept 512 KiB behind what was sent (more than the vsock has in flight) and read at most 256 KiB ahead (the command waits rather than output being lost); an orphaned command runs 60 s for its host to come back, a finished one's result is kept 60 s, forgotten IDs are never run again. A changed instance (the agent restarted) or a forgotten command fails with `Error::ConnectionReset`; a stopped guest with `Error::GuestGone`.
- **virtio-net and the egress policy (board 13097):** optional (`MachineConfig::network`, off by default: a sandbox has no network unless asked), PCI 00:03.0, features MAC, MTU (65520: large frames instead of checksum/TSO offloads) and MRG_RXBUF. The other end is a smoltcp 0.12 stack in AnyIP mode on a network thread of its own (the device thread only moves frames): the guest is `10.0.2.2/30` with hostname `guest`, configured by `ip=` on the kernel command line (needs `CONFIG_IP_PNP`; ~15 ms of boot), and the VMM is its gateway and DNS server at `10.0.2.1`, which also stands for the host's loopback. A guest SYN is held while the VMM connects from the host with an ordinary non-blocking socket; then a smoltcp socket listening on exactly that destination takes the replayed SYN, or, if the policy denied it or the host connect failed, smoltcp answers the replayed SYN with RST (connection refused, at once). TCP only, IPv4 only; UDP reaches only the DNS server (A records from the host's resolver for names the policy could allow, AAAA empty, NXDOMAIN otherwise); ICMP echo only to the gateway. The policy (`net::EgressPolicy`): ordered rules (allow/deny, host pattern, port range), first match wins, default deny; host patterns `*`, IP, CIDR, DNS names (exact or `*.domain`, matched against the names the guest resolved through the VMM); `*` and names match only globally routable addresses (no loopback, private, link-local or metadata addresses: those need an explicit IP/CIDR rule), against SSRF and DNS rebinding. Changeable at runtime (`Machine::network()`). Limits: 128 connections, 256 KiB buffers each way. **Around the policy (board 13151, board 13157):** an `ask` rule hands a connection to the caller's `Decider` (a callback with a timeout, default 10 s, and a default verdict, default deny), called on a decider thread of its own per machine, one question at a time, never on the network thread; the guest's SYN waits for the answer or the deadline (then the default; a late answer is ignored; a panic or no answer is the default too; questions whose time ran out are not asked); no decider means deny. Python deciders run with the GIL on that thread and are not called once Python is exiting. Every connection is logged when it ends (denied ones at once): guest port, host address and port, the names it went by, verdict, what decided it (rule, no rule, callback, callback timeout/failed, no callback, connection limit), whether the host connection was made, bytes each way, start time and duration, in a ring per machine (`NetworkConfig::log_capacity`, default 1024) the caller drains (`Network::take_log`), the oldest dropped and counted when full; `Network::stats` gives counters (connections allowed/denied/failed/open, bytes each way live, DNS queries and refusals, decisions asked/timed out/failed, log records dropped). DNS answers carry `NetworkConfig::dns_ttl` (default 60 s; the host's getaddrinfo gives no TTL, so the VMM is the authority), and a name learnt from one matches name rules for its addresses for exactly that long, open connections staying. Caller-set host entries (`net::Hosts`, runtime `Network::set_hosts`) are answered by the VMM's DNS before the host's resolver, only for names the policy could allow, 127.0.0.1 answered as the gateway; a name rule matches an entry's addresses whatever they are (the caller set the mapping), while learnt names still match only global addresses. Fuzzed: `crates/libmachine/fuzz` (`net_frames`: the whole guest ingress with a fake host; `dns_query`).

## Snapshots
- **Taking one (board 13095):** `Machine::snapshot(path)` between runs (every vCPU parked: `&mut` means no `Run` exists; each vCPU finishes the access of its last exit with `KVM_RUN` and `immediate_exit` whenever a run ends, so the state read is what the guest resumes from). The device thread is held off by holding every virtio transport's lock for the whole snapshot, so nothing writes guest RAM meanwhile. PC machines without a network only: a networked machine's connections are host sockets no clone could share, so it is refused, as is device memory no device saves (board 13139's extent window will save its own).
- **The file:** a 64-byte header (magic, format version, state length, RAM offset, the state's SHA-256), the state (own little-endian codec; KVM's structures as their UAPI bytes), then each RAM region at a 2 MiB multiple, zero pages left as holes. Written beside its path, synced and renamed over it, read-only for its owner (clones map it: it must not change under them). The state: CPU model and fingerprint, vCPU count, RAM size and the whole memory layout; KVM's PICs, I/O APIC, PIT, kvmclock and TSC frequency; per vCPU MP state, regs, sregs, XSAVE2, XCRs, debug registers, LAPIC, every MSR KVM saves (its index list plus the MTRRs and PAT), pending events; the UART; per PCI function its configuration space, MSI-X table, masks and pending bits, the virtio common configuration, every queue's settings and ring positions, and its device's own state with a version of the device's (rng: none; vsock: the rx buffers it holds) — where board 13139's extent device adds its part.
- **Restoring:** `Snapshot::open(path)` checks a file once; `Machine::restore(&snapshot, config)` makes a machine from it, any number of times, from any thread. Refused, never converted: another format version, a damaged file, a config of another vCPU count, RAM size (whole memory layout compared), a CPU model whose fingerprint on this host differs, a TSC frequency KVM cannot scale to, a network. The machine is built as `boot_linux` builds it (same devices, BARs, GSIs; no kernel loaded), KVM's state is put back, then the devices', redoing what the hypervisor holds (ioeventfds and shared memory at the guest's BARs, MSI routes, irqfds); every active queue's vector is signalled once.
- Guest RAM is a MAP_PRIVATE copy-on-write mapping of the snapshot file: a clone's writes never reach the file or other clones; untouched pages share the page cache.
- **Clock:** kvmclock is set to its snapshot value plus the real time elapsed since, every vCPU's TSC moved on by as many cycles (one KVM_SET_MSRS, the TSC before the TSC deadline), and KVM_KVMCLOCK_CTRL tells the guest it was paused: wall and monotonic clocks are right whichever clocksource the guest uses.
- **RNG:** every PC has a VM generation ID (Microsoft VMGENID: ACPI `VGEN`, _CID `VM_Gen_Counter`, 16 bytes at 0xFF000 in the reserved BIOS area) and a Generic Event Device (ACPI0013 on GSI 16, an I/O APIC pin the legacy PIC never sees); a restore writes a fresh ID and raises the event, and Linux's vmgenid driver reseeds the CRNG. That happens asynchronously in the guest, so before anything runs the agent reseeds too: each restore gives the vsock a fresh random generation, and the agent client's first exchange with an agent behind it is `Reseed` (host entropy mixed in with RNDADDENTROPY, then RNDRESEEDCRNG), every exec after it. Guest kernels need `CONFIG_VMGENID` (cladefs's has it).
- **vsock:** a restored device sends the guest a transport reset event, so it drops connections from before the snapshot; new connections wait until it has taken it (the guest's repost of its event buffer notifies the device), and its host ports carry on from the snapshot's. Agent instance IDs stay what they were (each clone's client is new; request IDs are random); commands running at the snapshot keep running, orphaned, in every clone.
- Measured (256 MiB, 1 vCPU, release build, this host's ZFS): a snapshot ~55-200 ms (RAM scan and sync), opening one ~45 µs, a restore ~2.5 ms (median of 20; p90 3.5 ms), the agent's first answer (with its reseed) ~8 ms and a first command ~12 ms after the restore began (board 13177; 19 and 22 ms before the guest's repost notified the device). What bounds it: ~1.3 ms of the restore is KVM's memslot update (an SRCU grace period), and the restored guest's first touches of memory (an EPT fault and a host fault on the file mapping each) make it take ~3 ms to take the vsock reset and ~2.5 ms more for the agent's exchanges.
- **Sandboxes from a snapshot (board 13167):** `Sandbox::snapshot(path)` snapshots a running sandbox (its run thread pauses the machine between runs and runs it on), the way to make a template; `Sandbox::from_snapshot(Arc<Snapshot>)` creates sandboxes from it, ready once the agent answered after its reseed (Python `AsyncSandbox.snapshot()` / `AsyncSandbox.restore()`). Measured (board 13181, examples/snapshot_clones.rs, test kernel, loaded shared host): ~6 ms per sandbox one at a time (boot: ~77 ms; cladefs's kernel 7 ms against 345 ms); 10 at once ~11 ms each, 100 at once ~200 ms each (restores contend in the host kernel when made at once in one process); ~1.5 MiB private per clone (2.4 MiB with cladefs's kernel), the file's page cache (4-7 MiB) shared.
- The extent device follows doc-4's snapshot protocol (board 13139): the guest's Fxfs is frozen (`FREEZE`) before the snapshot, which is refused otherwise; the snapshot records what the window maps, not its memory; a restore forks the store from the snapshot's point and maps the window again at the same guest physical address.
- Restore in under 10ms is an *aspirational* target, not a hard requirement.
- A restore for a new tenant must give: fresh entropy (RNG reseed / vmgenid), a correct clock, no dirty pages shared between clones, and per-VM resource caps plus a kill switch.

## Security and tenancy (decision)
- The VMM runs inside the caller's process and restricts its own threads: seccomp filters on vCPU and device threads on Linux. On macOS and Windows we rely on Rust's memory safety and a small device set (acceptable while they are developer platforms).
- **One libmachine process may run VMs for many tenants.** This is a deliberate departure from cladefs's integrator model, which treats each VM process as compromised and jails one VM per process with a per-tenant daemon socket. Accepted risk: a guest escaping into the VMM reaches every tenant's daemon socket and stores held by that process. Callers that need cladefs's isolation can still run one process per tenant.
- Guest-facing parsers (virtio queues, the extent device's requests, smoltcp) must be fuzzed. The network's are (board 13097, `crates/libmachine/fuzz`).

## macOS (decision, 2026-11-26)
- macOS runs the same extent device as Linux, **with DAX** (the user's goal; it overturns libmachine's decision-4, which had dev platforms run it without DAX). cladefsd runs on the Mac (board 13065), and libmachine there maps the window's pages into the guest itself (board 13069). The device without DAX comes first (board 13067), as a step.
- HVF builds and VM tests run on the user's Mac: hotbed has no macOS node and GitHub's M1 runners cannot nest Hypervisor.framework.
